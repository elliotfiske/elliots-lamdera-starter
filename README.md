# Elliot's Lamdera Starter

A starter for [Lamdera](https://lamdera.com) apps (full-stack Elm). It comes
set up with:

- end-to-end tests that run at unit-test speed, using `lamdera/program-test`
- elm-review
- Tailwind
- automatic preview and production deploys from GitHub Actions
- tooling for AI coding agents, both on your machine and in Claude Code
  cloud sessions

The app itself is deliberately tiny: a frontend, a backend, and a "Ping"
button that makes a round trip over Lamdera's frontend↔backend channel. It
also includes an example HTTP RPC endpoint.

## Quick start

You need Node 22 and the Lamdera compiler. Install the pinned version with
`bash scripts/install-lamdera.sh` (Linux x86-64), or get it from
<https://dashboard.lamdera.app/docs/download>.

```bash
npm install     # also points git at the repo's hooks (.githooks/)
npm start       # lamdera live + Tailwind watcher + a debuggable Chrome
npm test        # end-to-end tests (elm-test-rs + lamdera/program-test)
npm run review  # elm-review
```

`npm start` picks free ports and prints the app's URL, usually
<http://localhost:8000>. It restarts `lamdera live` if it crashes, and
`--no-chrome` skips opening the browser.

## Testing

`npm test` runs `tests/E2ETests.elm` with
[`lamdera/program-test`](https://package.elm-lang.org/packages/lamdera/program-test/latest/).
Tests drive real frontends and the backend (clicks, `ToBackend`/`ToFrontend`
messages, simulated time and HTTP) without a browser, so they're fast and
deterministic. The `.claude/skills/testing-*` and `red-green-tdd` skills
cover the patterns.

## Deploying

Lamdera deploys are git pushes to `git@apps.lamdera.com:<app>.git`. Pushing
`main` updates production. Pushing any other branch creates a **preview app**
at `<app>-<branch>.lamdera.app`. Previews skip Evergreen and reset their
backend on every deploy. The app name lives in `package.json` →
`config.lamderaApp`, currently `elliot-cloud-code-test`.

GitHub Actions does all of this:

| Workflow | Runs on | Does |
|---|---|---|
| `tests.yml` | PRs and pushes to `main` | elm-review, `npm test`, and (on PRs) `lamdera check --force`, the Evergreen migration gate |
| `preview.yml` | Every PR push (same-repo only) | Pushes to `pr-<N>` → `https://<app>-pr-<N>.lamdera.app`, screenshots the app, and keeps one PR comment updated with the link and screenshots |
| `deploy.yml` | Every merge to `main` | `npm run deploy` → production at `https://<app>.lamdera.app` |

**Required repo secrets:**

- `LAMDERA_SSH_KEY`: a private ed25519 key whose public half is added in the
  Lamdera dashboard. Needed for previews and deploys.
- `LAMDERA_CLI_AUTH`: the contents of `~/.elm/.lamdera-cli` (a single UUID,
  created by `lamdera login`; it's a dotfile, so use `ls -a`). Needed for
  `lamdera check`. Treat it as account-wide.

You can still deploy by hand: `npm run deploy` from an up-to-date `main` on
the primary checkout. `scripts/deploy.sh` refuses to run if the tree is
dirty, `main` has diverged from `origin/main`, or a migration is missing.

## Evergreen migrations

Lamdera hot-deploys new versions without dropping production data, but it
needs a migration whenever a persisted type changes. That's anything
reachable from the models or message types in `src/Types.elm`. Before
opening a PR that touches types:

```bash
lamdera check --force   # off main, --force checks against production
```

If types changed, this generates `src/Evergreen/V<N>/…` and
`src/Evergreen/Migrate/V<N>.elm`. Replace any `Unimplemented` placeholders,
then commit `src/Evergreen/` with the PR. Three things enforce this:

- the pre-push hook (`.githooks/pre-push`)
- CI's Evergreen check
- `deploy.sh`

See `.claude/skills/lamdera-deploy/SKILL.md` for the full workflow.

## Config (`Env.elm`)

`src/Env.elm` holds per-environment values. Lamdera **refuses to deploy**
an app while any `Env` value the code actually uses has no production value
set in the dashboard. That includes every preview app, since each one is a
separate app. Keep secrets out of git: a pre-commit hook blocks commits
where `src/Env.elm` differs from `Env-Clean.elm`. Set real values locally
and in the Lamdera dashboard.

## Claude Code cloud sessions

The repo is set up so cloud agents (claude.ai/code) can build, test,
`lamdera check`, run the app, and take screenshots. A SessionStart hook,
`.claude/hooks/cloud-setup.sh`, runs only in cloud sessions. It:

- installs the pinned Lamdera binary (`scripts/install-lamdera.sh`) and npm
  dependencies;
- fills `~/.elm` with `scripts/elm-prefetch.js`. The cloud network blocks
  the compiler's own package downloads from GitHub, but plain `git clone`
  works;
- writes the Lamdera CLI auth from the `LAMDERA_CLI_AUTH` environment
  variable. Add it in the cloud environment's settings so agents can run
  `lamdera check`;
- adds the `lamdera` git remote and enables the repo's git hooks.

Cloud containers **can't push to Lamdera**, because SSH is blocked. Agents
deploy by pushing to a PR (preview) or getting it merged (production).

For visual checks, `npm start` runs headless Chromium on Linux, and the
`scripts/cdp-*.js` tools work as they do locally. There's also:

```bash
node scripts/screenshots.js --base http://localhost:8000 --out screenshots
```

It captures every route × viewport listed in `scripts/screenshot-routes.json`;
CI uses the same list for PR comments.

More detail, including debugging frontend state over Chrome DevTools
Protocol and reading the backend model with `lamdera backend`, is in
[CLAUDE.md](CLAUDE.md).

## Tooling notes

- **Lamdera version** is pinned with a SHA-256 checksum in
  `scripts/install-lamdera.sh`. Bump the version and hash together.
- **elm-review** uses the real `elm` binary from the `@lydell/elm`
  devDependency (`lamdera` can't stand in for it). It runs after every file
  edit through a Claude Code hook. Vendored code and `src/Evergreen/` are
  exempt.
- **Tailwind** v3 (standalone CLI). The pre-commit hook rebuilds
  `public/output.css` and updates its cache-busting hash.
